# 📦 Mesh Graph Blob Format

The navigation graph is a single blob asset. This page lists exactly what is inside it, how big it is, and the rules that keep it valid.

## 🧱 The seven pools

```text
BnMeshGraphBlob
├── Vertices        : BlobArray<float2>       // all polygon corners, graph space (XY)
├── Polygons        : BlobArray<BnPolygon>    // centre + vertex/neighbour slices
├── NeighborPolygons: BlobArray<int>          // neighbour ids, grouped per polygon
├── Links           : BlobArray<BnLinkData>   // directed portals
├── PolyLinkOffsets : BlobArray<int>          // first link index per polygon
└── PolyLinkCounts  : BlobArray<int>          // links leaving each polygon
```

Access is always *offset + count* pairs, never a linked structure: A* walks the link pool sequentially from `PolyLinkOffsets[polygon]` for `PolyLinkCounts[polygon]` entries, which is exactly what Burst needs to vectorize and prefetch.

## 📐 Struct sizes

| Struct | Fields | Bytes |
|---|---|---|
| `BnPolygon` | `Center: float2` (8) + `VertexOffset: int` (4) + `VertexCount: int` (4) + `NeighborOffset: int` (4) + `NeighborCount: int` (4) | **24** |
| `BnLinkData` | `PortalLeft: float2` (8) + `PortalRight: float2` (8) + `Target: int` (4) + `Cost: float` (4) | **24** |
| vertex | `float2` | **8** |

Field order is already size-descending (8-byte, then 4-byte members), so no alignment padding is inserted.

## 🔢 Pool sizes for a grid

`BnMeshAuthoringBaker.BuildGraph` emits a non-indexed grid: each polygon owns its own four vertices and all links are materialised in both directions.

| Pool | Size for `CellsX × CellsY` |
|---|---|
| `Polygons` | `X * Y` |
| `Vertices` | `4 * X * Y` |
| `Links` | `2 * ((X-1) * Y + X * (Y-1))` |
| `NeighborPolygons` | same as `Links` |
| `PolyLinkOffsets` / `PolyLinkCounts` | `X * Y` each |

Polygon id is row-major: `id = y * CellsX + x`. The four vertices of polygon `id` are its lower-left corner, then clockwise: `(x, y)`, `(x+1, y)`, `(x+1, y+1)`, `(x, y+1)`, scaled by `CellSize` and offset by `Origin`.

### Example: 4 × 4 grid, `CellSize = 1`

| Pool | Count | Bytes |
|---|---|---|
| `Polygons` | 16 | 384 |
| `Vertices` | 64 | 512 |
| `Links` | 24 | 576 |
| `NeighborPolygons` | 24 | 96 |
| `PolyLinkOffsets` | 16 | 64 |
| `PolyLinkCounts` | 16 | 64 |
| **Total (payload)** | | **≈ 1.7 KB** |

### Example: 100 × 100 grid, `CellSize = 1`

| Pool | Count | Bytes |
|---|---|---|
| `Polygons` | 10 000 | ≈ 234 KB |
| `Vertices` | 40 000 | ≈ 313 KB |
| `Links` | 39 600 | ≈ 928 KB |
| `NeighborPolygons` | 39 600 | ≈ 155 KB |
| `PolyLinkOffsets` + `PolyLinkCounts` | 10 000 each | ≈ 78 KB |
| **Total (payload)** | | **≈ 1.7 MB** |

Add roughly 29 bytes per polygon for the A* scratchpad (≈ 290 KB here), and keep in mind both live for the whole level.

> 💡 **Vertex duplication is the price of a non-indexed grid.** Sharing corners between polygons would cut `Vertices` by ~4×, but the blob would need an index pool and the funnel would lose its direct corner reads. At the sizes Free targets, the duplication is cheaper than the indirection.

## 🔒 Immutability rules

| Rule | Consequence of breaking it |
|---|---|
| The blob never changes after `CreateBlobAssetReference` | Jobs read it without a job dependency of their own. |
| Exactly one `BnBlobMeshGraph` per world | Both systems early-out on zero **or multiple** matches — the pipeline silently stops. |
| The creator disposes the blob | Authoring-baked blobs are owned by the baking system; `BuildGraph` blobs are yours to `Dispose()`. |
| Never swap the blob while searches are in flight | Existing corridors reference polygon ids that a new blob may no longer contain. |

## 🛠️ Building a blob yourself

Only `BnMeshAuthoringBaker.BuildGraph(cellsX, cellsY, cellSize, origin)` is public; the `BlobBuilder` path is internal. That means custom geometry has two options:

1. **Compose from grids.** Bake several `BnMeshAuthoring` entities — each produces its own graph, but only one may be the singleton, so grids are usually combined into a single level grid instead.
2. **Write your own builder.** Build a `BnMeshGraphBlob` with `BlobBuilder`, keeping the invariants below, then assign it to a `BnBlobMeshGraph` entity.

### Invariants for a hand-built blob

| Invariant | Check |
|---|---|
| Every `BnPolygon` is convex | The funnel assumes convex portals between neighbours. |
| `Target` of every link is a valid polygon id | `0 <= Target < PolygonCount`. |
| `PolyLinkOffsets[p] + PolyLinkCounts[p] <= LinkCount` | No slice may overrun the link pool. |
| `VertexOffset + VertexCount <= VertexCount` (the pool length) | Vertex slices must stay in the pool. |
| `NeighborOffset + NeighborCount <= NeighborPolygons.Length` | Neighbour slices must stay in the pool. |
| Link order matches neighbour order | `GetNeighbor(p, i)` should be the polygon reached by `GetPolyLink(p, i)`. |
| `PortalLeft`/`PortalRight` are the shared edge | The funnel reads portal midpoints, not polygon centres. |
| A non-positive `Cost` is intentional | It means "use centre-to-centre distance". |

> ⚠️ A malformed blob does not throw. The search will still run and produce a corridor that the funnel cannot follow, so validate custom blobs with a one-off EditMode test against a small grid.

## 🧠 Scratchpad layout (for reference)

`BnPathScratchpad` is **not** uniformly indexed — the distinction matters if you inspect it:

| Array | Length | Indexed by |
|---|---|---|
| `GScore`, `CameFrom`, `HeapSlots`, `Closed`, `Path` | `Capacity` | polygon id |
| `HeapPolygons`, `HeapKeys` | `Capacity + 1` | heap slot (extra slot allows a speculative push without a bounds check) |
| `VisitStamp` | `Capacity + 1` | polygon id (last slot holds `SearchId`) |

`VisitStamp` plus `SearchId` is how a new search invalidates the previous one by incrementing a counter instead of clearing five arrays. When the counter wraps, the rest of the array is cleared once. `HeuristicScale` survives `EnsureCapacity`; every other field is search state.
