# ⚠️ Limitations & Scope

Free is built for **small static levels with a modest number of agents**. The limits below follow directly from the architecture, so plan around them instead of trying to tune them away.

## 📉 Flat search scaling

Every request runs one flat A* over the whole polygon graph. Cost grows with the number of expanded polygons, and every agent searches the same graph from scratch — there is no cluster decomposition, no abstract graph and no precomputed long-distance route table.

| Graph size | Behaviour |
|---|---|
| Tens to a few thousand polygons | The default 4096-expansion budget covers typical paths. |
| Several thousand polygons | Raise `MaxIterations` or long routes may fail. |
| Tens of thousands of polygons | Each request becomes expensive, and the scratchpad grows with the graph. |

The scratchpad is O(polygon count) in memory — roughly 29 bytes per polygon plus 12 bytes of spare heap and visit-stamp slots. It is reused, so it never allocates per frame, but it must cover the whole graph: a large graph has a fixed memory floor even when agents only travel short distances.

Pathfinding is also all-or-nothing. When the budget runs out, the request becomes `BnPathStatus.Failed` and the corridor is cleared — Free never emits a partial path for the agent to follow toward the target.

## 👥 No crowd avoidance

Free has no neighbour query and no local avoidance solve. `KinematicBypassJob` copies `DesiredVelocity` into `Velocity` unchanged, so every agent follows its funnel as if no other agent existed.

Observable effects:

* Agents on crossing paths can overlap.
* A stopped agent does not block or deflect a moving agent.
* Dense groups do not separate, queue or spread out around corners.
* Throughput through a narrow portal is not regulated.

The funnel still produces smooth single-agent paths through portal edges. What is missing is social: nothing in Free reads another agent's position or velocity during steering.

If your design needs separation, provide it outside the runtime — spaced spawn points, one-way lanes, staggered start times. A custom post-steering separation job replaces the Free steering contract and is therefore not part of the supported pipeline.

## 🧱 No dynamic obstacles

The navigation graph is an immutable blob asset. There is no runtime obstacle store, no obstacle query and no broadphase to update when a blocker moves.

* Moving a wall, crate or vehicle does not change the graph or the agent paths.
* An agent keeps following its corridor even if something now occupies it.
* Adding or removing blocked regions requires rebuilding the blob and replacing the graph singleton.
* There is no built-in push-out when an agent overlaps a static or moving blocker.

You can bake a different graph for a different level state, but swapping graphs at runtime invalidates existing corridors and can force every agent to repath. That is not a supported dynamic-obstacle workflow.

## 🚪 No door or area tags

Free links carry no door or area tags, and `BnPathfindingSystem` always runs the unfiltered A* overload. Every portal in the graph is traversable.

* You cannot close a doorway for one agent and leave it open for another.
* You cannot route around a locked area through the Free systems.
* Access control must be enforced by gameplay before a request is issued, and the graph must not contain the forbidden region.
* A closed door is a graph change — a rebake and a repath, not a per-link flag.

`BnAStar.FindPath` does expose filtered overloads that take a `BnLinkFilter` plus an optional per-link tag-mask array, and `BnLinkFilter` ships in this assembly. Using them requires your own job or system: `BnPathfindJob` always passes `BnLinkFilter.PassThrough` with no tag masks, so a filtered search is not reachable through `BnPathfindingSystem`.

## 🌐 Static graph, one owner

Free assumes one static graph per world:

* Exactly one `BnBlobMeshGraph` singleton. Both systems skip their work when there is none — and when there is more than one.
* A graph must exist before agents request paths: `BnPathfindingSystem` returns early while `graph.Value` is not created.
* Topology is fixed for the lifetime of the blob. Replacing the blob while searches are in flight is not supported by the Free systems.

## 📐 2.5-D navigation

Paths and steering are solved on **XZ only**:

* No ramp or stair following, and the pipeline never modifies agent Y — vertical movement is gameplay's job.
* A multi-floor level flattens into one plane, so a "vertical" route is a straight XZ shortcut.
* Polygons must be convex, and `BnMeshAuthoring` produces axis-aligned squares only.
* A spawn or destination far outside the mesh resolves to the nearest polygon rather than failing, which can look like a path that starts in the wrong place.

## 🧩 Choosing the right tool

| Your level needs | Free | Notes |
|---|---|---|
| Dozens of agents on a static grid | ✅ | The intended use case. |
| A few thousand polygons with short routes | ✅ | Keep `MaxIterations` ≥ reachable polygon count. |
| Crowds that queue at doors | ❌ | No separation stage to tune. |
| Obstacles that move mid-game | ❌ | Graph is immutable. |
| Per-agent door access | ❌ | No link tags in the pipeline. |
| One agent, one corridor, zero allocation | ✅ | 100 % Burst, no main-thread sync. |

## 🔧 Extending beyond Free

Free stops at the architecture on this page. If a level needs more, the options are:

* Replace or wrap the steering system when agents must stay apart in crowds, queues or narrow corridors.
* Replace the pathfinding job when the flat search is the frame-time bottleneck, long routes hit `MaxIterations`, or paths need a different filter.
* Rebuild and swap the graph blob when obstacles move or the level changes — never while searches are in flight.
* Enforce doors and areas before a request is issued, or write a filtered search job around `BnAStar.FindPath`.

Each option replaces a **pipeline stage** rather than changing a field, because the package deliberately exposes no extension points: six agent components, five jobs and two systems are the whole contract.
