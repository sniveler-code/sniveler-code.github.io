# 🧩 Components & Systems

This page is the complete contract: every component layout, every job's inputs and outputs, and the order the systems run in.

## 🧾 Graph component

| Type | Kind | Fields |
|---|---|---|
| `BnBlobMeshGraph` | `IComponentData` | `Value: BlobAssetReference<BnMeshGraphBlob>` |

The component grants one entity ownership of an immutable navigation graph. The blob reference keeps topology out of the component, so a job reads the graph without copying arrays or resolving components per agent. The world owns the component; whoever created the blob owns and disposes the reference.

## 🤖 Agent archetype

`BnAgentComponents.CreateAgentArchetype(EntityManager)` produces exactly one archetype:

| Component | Type | Written by |
|---|---|---|
| `BnAgentSteering` | `IComponentData` | `BnFunnelJob`, `KinematicBypassJob`, `IntegrateJob` |
| `BnAgentPath` | `IComponentData` | `BnPathfindJob`, `BnFunnelJob` |
| `BnPathWaypoint` | `IBufferElementData` | `BnPathfindJob` |
| `BnAgentPathRequest` | `IComponentData` | gameplay, `BnPathfindJob` |
| `BnAgentSteeringActive` | `IEnableableComponent` | `BnSteeringStateJob` (via ECB) |
| `BnAgentPathRequestPending` | `IEnableableComponent` | `BnPathfindJob` (via ECB) |

> 💡 **One archetype, always.** Do not add optional marker components per agent — every extra component splits the logical agent into a new archetype and costs you chunk density. If you need a gameplay flag, put it in `BnAgentFlags.Blocked` or in a component that **every** agent has.

`BnAgentComponents.DefaultPathCapacity` is `16`: the inline `BnPathWaypoint` capacity before the buffer spills to heap storage. A corridor longer than 16 polygons allocates once for that agent — the only heap traffic in the whole pipeline, and it only happens on long paths.

## 🔍 `BnAgentSteering` in detail

| Field | Meaning | Owner |
|---|---|---|
| `Position` | World position. XY is the navigation plane, Z is height. | `IntegrateJob` |
| `Velocity` | Resolved velocity. | `KinematicBypassJob` |
| `DesiredVelocity` | Requested velocity from the funnel. | `BnFunnel.Solve` |
| `MaxSpeed` | Upper bound in units per second. | authored |
| `Radius` | Agent radius — also the arrival tolerance. | authored |
| `PathProgress` / `PathLength` | Completed segment length and total length. | `BnFunnel` |
| `WaypointIndex` | Cursor into the corridor. | `BnFunnel` |
| `Flags` | `Following`, `Arrived`, `Blocked`. | `BnFunnel` |

| Member | Semantics |
|---|---|
| `Idle(float3 position, float maxSpeed, float radius)` | Zero velocity, `BnAgentFlags.None`, no path. |
| `HasPath` | `PathLength > 0 && (Flags & Following) != 0`. |
| `NormalizedProgress` | `PathProgress / PathLength` saturated to 0..1, or 0 without a path. |

Both properties are branch-free, read-only and take no allocation.

> ⚠️ **Never write `PathProgress`, `PathLength` or `WaypointIndex`.** The funnel owns them; overwriting them corrupts the cursor and makes the agent walk backwards along its corridor.

## 🧠 Also worth knowing

| Type | Fields | Notes |
|---|---|---|
| `BnPathWaypoint` | `Position`, `ExitPoint`, `PolyIndex`, `LinkIndex` | `Create(position, exitPoint, polyIndex, linkIndex)` copies the four arguments unchanged. `LinkIndex = -1` on the final waypoint. |
| `BnAgentPathRequest` | `Start`, `Target`, `RequestId`, `StartPoly`, `TargetPoly`, `Status` | `Create(start, target, requestId)` starts as `Pending` with both polygon ids at `-1`. |
| `BnAgentPath` | `PathIndex`, `WaypointCount`, `Status` | `PathIndex` is a stable identity you assign; Free never renumbers it. |
| `BnPolygon` | `Center`, `VertexOffset`, `VertexCount`, `NeighborOffset`, `NeighborCount` | Blob struct, read-only after bake. |
| `BnLinkData` | `PortalLeft`, `PortalRight`, `Target`, `Cost` | Blob struct; `Cost <= 0` means "use centre-to-centre distance". |

## ⚙️ Jobs

| Job | Interface | Input | Output |
|---|---|---|---|
| `BnPathfindJob` | `IJobChunk` | `BnAgentPathRequest`, `BnAgentPath`, `BnPathWaypoint` buffer, enabled `BnAgentPathRequestPending`, graph singleton | `BnAgentPathRequest`, `BnAgentPath`, waypoint buffer, `SetComponentEnabled<BnAgentPathRequestPending>(false)` |
| `BnFunnelJob` | `IJobChunk` | `BnAgentSteering`, `BnAgentPath`, waypoint buffer, `BnAgentSteeringActive`, graph singleton | `BnAgentSteering` |
| `BnSteeringStateJob` | `IJobChunk` | `BnAgentPath`, `BnAgentSteeringActive` | `SetComponentEnabled<BnAgentSteeringActive>` commands |
| `KinematicBypassJob` | `IJobChunk` | `BnAgentSteering` (active query) | `BnAgentSteering.Velocity` |
| `IntegrateJob` | `IJobChunk` | `BnAgentSteering` (active query) | `BnAgentSteering.Position` |

Behavioural details that are easy to miss:

* **`BnPathfindJob`** expands one flat A* per pending agent into the **shared** scratchpad, so it schedules single-threaded. Required toggle state is enforced by the query (`BnAgentPathRequestPending` enabled), and the job records the toggle-off command rather than writing enable bits directly.
* **`BnFunnelJob`** runs on a query built with `EntityQueryOptions.IgnoreComponentEnabledState`, so disabled agents are still visited and a freshly assigned path can reactivate them. It calls `BnFunnel.Solve` on a local copy and does **not** write the path slot or the buffer back.
* **`BnSteeringStateJob`** derives `IsSteerable` from `BnAgentPath.IsFollowable` and records the toggle in a `ParallelWriter`, so it can run in parallel with the funnel job.
* **`KinematicBypassJob`** and **`IntegrateJob`** run on the *active* query and skip disabled agents through `ChunkEntityEnumerator`. `IntegrateJob` is branch-free and uses `math.mad`.

## 🏗️ Systems

| System | Group | Fields | Owns |
|---|---|---|---|
| `BnPathfindingSystem` | `SimulationSystemGroup` | `MaxIterations` (default `DefaultMaxIterations = 4096`), properties `HasScratchpad`, `ScratchpadCapacity` | one persistent `BnPathScratchpad` |
| `BnSteeringSystem` | `SimulationSystemGroup`, `[UpdateAfter(BnPathfindingSystem)]`, `[UpdateBefore(EndSimulationEntityCommandBufferSystem)]` | none | no native memory |

### System order

| Order | Who | Work |
|---|---|---|
| 1 | your tuning system (`InitializationSystemGroup`) | one-shot field assignment |
| 2 | your request system (`SimulationSystemGroup`, before `BnPathfindingSystem`) | write target, arm the request |
| 3 | `BnPathfindingSystem` | flat A* and corridor write |
| 4 | `BnSteeringSystem` | funnel → bypass → integrate |
| 5 | `EndSimulationEntityCommandBufferSystem` | single command playback |

`BnPathfindingSystem` declares only `[UpdateInGroup]`; its command buffer is ordered by `AddJobHandleForProducer`, which makes the barrier wait for the pathfind job instead of relying on an `UpdateBefore` attribute. `BnSteeringSystem` registers its final handle with the same barrier, so both toggle changes play back once per frame.

### Scratchpad resizing

When a bound graph outgrows the scratchpad, `EnsureScratchpad` allocates a new one, swaps it in, and calls `Dispose(JobHandle)` on the old arrays with the in-flight search handle. The update is never skipped and the system never calls `Complete` on the main thread. Never resize or dispose that scratchpad from gameplay code.

## 🧵 Threading rules that keep the pipeline valid

| Rule | Why |
|---|---|
| Never call `Complete()` on the pathfinding or steering handles from `OnUpdate` | Serializes the frame; read the components on a later frame instead. |
| Read and write components through chunk arrays, never per-entity `GetComponentData` in a loop | Each per-entity call is a random memory access into archetype storage. |
| Let the systems own the `EntityCommandBuffer` playback | One playback at frame end keeps toggles consistent within a frame. |
| Keep exactly one `BnBlobMeshGraph` singleton | Both systems early-out on zero or multiple matches. |
| Keep one dominant agent archetype | Denser chunks, better L1/L2 hit ratio during iteration. |
