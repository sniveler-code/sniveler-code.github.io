# 🏎️ Performance & Tuning

The Free package has few tuning knobs on purpose: the search budget bounds worst-case pathfinding, and the agent steering fields define speed and stopping distance. Everything else is fixed by the zero-allocation job pipeline.

## 📊 Cost model

| Stage | Complexity | Threading |
|---|---|---|
| Polygon resolve + flat A* | O(expanded polygons) per request | single-threaded (one shared scratchpad) |
| Corridor write | O(corridor length) | same job |
| Funnel + progress | O(corridor length) per agent | parallel |
| Bypass | O(1) per agent | parallel |
| Integrate | O(1) per agent | parallel |

Pathfinding dominates, and it is serializer-bound by design: two searches cannot share one scratchpad. Steering, by contrast, scales linearly across cores because each agent owns its state and buffer.

Steady-state allocations are zero. The only heap traffic in the pipeline is a `BnPathWaypoint` buffer spilling past its inline capacity of 16 when a corridor is longer than 16 polygons — and only once per agent.

## 🎚️ `MaxIterations`

`BnPathfindingSystem.MaxIterations` is the maximum number of A* node expansions per request. Default: `DefaultMaxIterations = 4096`.

| Value | Effect |
|---|---|
| Too low | Long paths end as `BnPathStatus.Failed` and the corridor is cleared. |
| 4096 (default) | Covers most levels up to a few thousand polygons. |
| Larger | Tolerates longer or more obstructed routes, but bounds a bad request less tightly. |

One expansion pops one polygon and relaxes its outgoing links, so the budget only has to exceed the number of polygons the search expands **before it reaches the target**. An unreachable target drains the open set and stops early, which costs at most one expansion per reachable polygon. A budget cut-off is a separate outcome.

Set the field once, before agents start requesting paths:

```csharp
using Unity.Entities;

namespace BurstNav.Guide
{
    [UpdateInGroup(typeof(InitializationSystemGroup))]
    public partial class BnTuningSystem : SystemBase
    {
        private bool _applied;

        protected override void OnUpdate()
        {
            if (_applied)
            {
                return;
            }

            _applied = true;
            var pathfinding = World.GetOrCreateSystemManaged<BnPathfindingSystem>();
            pathfinding.MaxIterations = 8192;
        }
    }
}
```

`HasScratchpad` and `ScratchpadCapacity` let you assert at startup that the scratchpad covers the graph instead of discovering it on the first long request.

## 🧮 Memory

| Allocation | Lifetime | Size |
|---|---|---|
| Graph blob | level | see [Mesh Graph Blob Format](7.-blob-format.md) |
| A* scratchpad (system-owned) | level | ≈ 29 bytes per polygon + 12 bytes of spare slots |
| Waypoint buffers | per agent | 16 inline elements, then heap |

The scratchpad is allocated once per graph size, not per frame. When the graph outgrows it, the system allocates a replacement and retires the old arrays with `Dispose(JobHandle)` — never by completing the in-flight search on the main thread.

## 🏃 Speed and arrival

| Field | Effect |
|---|---|
| `MaxSpeed` | Upper bound of `DesiredVelocity` and `Velocity`, units per second. |
| `Radius` | Agent radius; also the effective arrival tolerance. |

The funnel computes desired speed as `Min(MaxSpeed, distance / deltaTime)`, so an agent cannot overshoot a waypoint at the end of a frame. The arrival test uses `max(Radius, BnFunnel.DefaultArrivalRadius)` — a larger `Radius` stops the agent further from the target, and a `Radius` below 0.05 still stops at 0.05.

> 💡 **There is no acceleration model.** The kinematic bypass changes velocity from zero to `MaxSpeed` in one frame. For smoother motion, lower `MaxSpeed` or replace the steering chain with your own acceleration-limited version before integration.

Changing the profile after baking is a one-shot write, never a per-frame edit:

```csharp
using Unity.Entities;

namespace BurstNav.Guide
{
    public static class BnAgentProfile
    {
        public static void Apply(EntityManager entityManager, Entity agent, float maxSpeed, float radius)
        {
            var steering = entityManager.GetComponentData<BnAgentSteering>(agent);
            steering.MaxSpeed = maxSpeed;
            steering.Radius = radius;
            entityManager.SetComponentData(agent, steering);
        }
    }
}
```

Read `PathProgress`, `PathLength`, `NormalizedProgress` and `WaypointIndex` for HUDs and logic; never write them.

## ⚙️ Burst and Jobs settings

| Editor setting | Development | Ship |
|---|---|---|
| Jobs → Burst → Enable Compilation | on | on |
| Jobs → Burst → Synchronous Compilation | only when debugging Burst code | off |
| Jobs → Safety Checks | on | off in release |
| Jobs → Leak Detection | on | on in development builds |

Runtime rules that keep the pipeline valid:

* Do not call `Complete` on the pathfinding or steering handles from gameplay; read state on a later frame instead.
* Do not write the system-owned `BnPathScratchpad`.
* Keep one dominant agent archetype and one `BnBlobMeshGraph` singleton.
* Do not spawn or destroy agents per frame; batch structural changes into a command buffer.

## 🔬 Measuring instead of guessing

| Question | Where to look |
|---|---|
| Is pathfinding the frame cost? | Profiler → Hierarchy → `BnPathfindingSystem`, or the Jobs breakdown for `BnPathfindJob`. |
| Are long paths failing? | Inspect `BnAgentPath.Status` and compare `scratch.Iterations` with `MaxIterations`. |
| Are agents overlapping? | Expected — see [Limitations & Scope](5.-limitations-and-scope.md). There is no separation stage to tune. |
| Are buffers spilling? | Entities Hierarchy → agent → `BnPathWaypoint` capacity vs `WaypointCount`. |
| Is the graph too big? | Count polygons: `LinkCount` and `PolygonCount` on the blob; compare against the budget table above. |

## 🚀 Optimisation order

If the profile says pathfinding is too slow for your level, in this order:

1. **Reduce graph size.** Bigger `CellSize` means fewer, larger polygons — the same level with a quarter of the polygons runs roughly four times cheaper per search.
2. **Request less often.** Paths are static; re-request only on a new destination, not every frame.
3. **Raise the budget only after measuring.** `MaxIterations` does not make searches faster — it makes more of them succeed.
4. **Spread requests over frames.** One or two long searches per frame keeps a stable frame time; a burst of 50 identical long searches does not.
5. **Replace the pathfinding stage** if you need hierarchical search or filtered long routes. That is an architecture change, not a setting.
