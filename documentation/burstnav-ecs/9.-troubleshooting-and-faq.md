# 🚑 Troubleshooting & FAQ

## Why do my agents stand still?

Check in this order:

1. **`Idle` state** — agents (authored or `BnAgents.Create`) start `Idle` and move only after `BnAgents.SetDestination(world, agent, pos)` (or a right-click via `BnCommandSystem`, which only targets `Idle` agents).
2. **Spawn too far from the mesh** — a spawn position more than one spatial-grid cell (2 m) from any polygon makes the first request end in `BnPathState.Failed`; the agent then stays put. Spawn agents on the mesh.
3. **No `BnGraphData` in the world** — the systems are inert until `BnMeshAuthoring` is baked (see "How do I re-bake…" below). If your world has no `BnMeshAuthoring` (or the scene with it was not loaded into the world, e.g. a missing SubScene), nothing runs.
4. **Off-mesh destination** — a target more than one cell from the mesh also fails the search (`Failed`).
5. **`BnPathRequestTag`** — the steering pipeline only integrates agents with an *enabled* `BnPathRequestTag`. If you hand-build agent entities, use `BnAgents.Create` — a missing or wrongly disabled tag freezes the agent silently by design.

## How do I re-bake after changing geometry?

1. Move the geometry (obstacles, walls, floor).
2. Re-bake the built-in `NavMesh` (Window → AI → NavMesh → Bake) so the static geometry is up to date.
3. Enter **Play Mode** — the runtime `NavMesh` (and therefore the triangulation `BnMeshAuthoring` reads) only exists while playing.
4. On the `BnMeshAuthoring` GameObject, run the context menu item **Bake NavMesh Data to Authoring** — this is the *only* way `CachedVertices`/`CachedIndices` are refreshed. If the runtime NavMesh is empty, the cache is left untouched and a red log tells you why.
5. Stop Play (or keep playing) — the `Baker` rebuilds the blob from the refreshed cache on every play session, so agents re-path onto the new mesh.

The blob itself is never persisted: it is rebuilt from the scene's cached triangulation on every play session, so older scenes always load correctly with newer package versions.

## Why are the `BurstNav/*` menus missing?

The verification harnesses compile only when the project defines `BN_INCLUDE_HARNESS` (by design — buyers of the package see no extra menus). To enable them, create `Assets/csc.rsp` with a single line:

```
-define:BN_INCLUDE_HARNESS
```

and let Unity recompile. `csc.rsp` works in interactive and `-batchmode` sessions; headless run: `-executeMethod SnivelerCode.BurstNav.Editor.BnHarnessRunner.RunAll`.

## Right-click commands don't work — why?

`BnCommandSystem` reads the **legacy input manager** (`UnityEngine.Input`). If your project uses the new Input System with the legacy manager *disabled*, the system is a no-op. **Note: the stock Unity 6 3D template ships with the legacy manager disabled** (Project Settings → Player → *Active Input Handling* = *Input System package only*), so in a fresh project the right-click path is inactive until you set it to *Both*. Two options: enable the legacy manager (*Active Input Handling* → *Both*), or issue destinations from code: `BnAgents.SetDestination(world, agent, position)`. The demo logs a warning at play start when the legacy manager is disabled.

Also note: right-click only commands agents whose `BnPathRequestTag` is **disabled** (i.e. `Idle` agents); agents already following a path keep their corridor. The click point is raycast against the scene (2000 m) with a fallback to the XZ ground plane, and it must be within one grid cell (2 m) of the mesh.

## Can I use stairs, ramps, or multi-floor maps?

No — BurstNav is 2.5-D (XZ only). There is no stair/ramp following and no per-floor layering: a multi-floor navmesh is flattened into one layer and a "vertical" path is a straight XZ shortcut. An agent's Y is never modified by the pipeline; vertical movement (snap-to-terrain, stair blending) is gameplay code's responsibility. See [Introduction & Overview](README.md) → Scope & Known Limitations.

## How do I visualize ECS agents?

The package ships **no rendering bridge** (no `Unity.Entities.Graphics` dependency). Options:

* The **BurstNav Demo** sample includes a small visualizer: a MonoBehaviour polls the agent entities' `LocalTransform`/`BnOrcaState` and drives ordinary GameObjects (capsules). Study it for the polling pattern — it is cheap for demo-scale agent counts.
* Roll your own bridge, e.g. an Entities-Graphics-based one if you already use `Unity.Entities.Graphics` in the project.

## How many path requests can I issue per frame?

`BnPathfindingSystem` caps throughput at `MaxAgentsPerFrame` (≈ 256 new path requests/frame). Excess requests are **deferred** (the agent stays `Requested`), not dropped — bursty spawning simply spreads over a few frames. If you see agents lagging behind after a mass spawn, that is the cap working; space out `SetDestination` calls or accept the few-frame lag.

## An agent got pulled back onto the map — what happened?

The steering pipeline keeps agents inside their corridor (containment clamp): a step that would leave the current/next corridor polygon is projected back onto the polygon boundary/link, and if the corridor is stale (agent pushed, dragged, or the map changed underneath) the agent re-requests a path from the clamped position instead of freezing. Agents are otherwise never teleported by the package.

## Are agent positions deterministic?

Bakes and searches are deterministic (same input → same blob → same paths), and the harness checks rely on it. The ORCA steering step is also deterministic for identical initial state and timing, so replaying the same frames reproduces the same trajectories on the same machine/build.

## Does the package depend on the Input System or Entities.Graphics?

No. Only: `com.unity.entities`, `com.unity.collections`, `com.unity.burst`, `com.unity.mathematics`, and the built-in `com.unity.modules.ai` (for `NavMesh.CalculateTriangulation()` at bake time).
