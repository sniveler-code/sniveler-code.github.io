👋 Introduction & Overview

BurstNav ECS is a hierarchical pathfinding (HPA*) + ORCA steering system for Unity DOTS/ECS. Navmeshes are baked once into an immutable blob graph with a spatial-grid index and an optional cluster graph; at runtime a Burst-compiled flat/HPA* A* search (zero steady-state allocation) produces polygon corridors, a funnel simplifies them into waypoints, and a spatial-hash + ORCA pipeline keeps hundreds of agents apart. Dynamic obstacles block links at runtime — no re-bake.

Whether you are building an RTS, a factory-automation game, or a swarm-survival project, BurstNav gives you scalable crowd navigation where NavMeshAgent hits its per-MonoBehaviour limits.

✨ Core Features

  • 🗺️ HPA* Hierarchical Pathfinding
    Short hops run flat A* over a grid-broadphased polygon graph; long paths (distance > threshold) run HPA* over the cluster graph with a refinement pass. The threshold is per-mesh.
  • 🚶 ORCA Crowd Steering
    2-D disk avoidance with spatial-hash neighbor discovery (MaxNeighbors = 48) and a corridor containment clamp that keeps agents on the mesh and out of walls.
  • 📦 Baked Immutable Blob Graphs
    One BlobAssetReference<BnBlobMeshGraph>: deduplicated portals, uniform XZ spatial grid, optional HPA* cluster layers. No per-frame allocation in the path hot path.
  • 🚧 Dynamic Obstacles Without Re-Bake
    Per-link blocking (SetLinkBlocked for debris) and door/water-style tag masks (BnDoorComponent + PolygonTagMasks). Affected agents re-path within 1–2 frames.
  • 🎲 Deterministic Bakes & Searches
    Same input → same blob → same paths. Re-baking is reproducible, and the shipped harness checks rely on it.
  • 🧪 EditMode Tests + Headless Harnesses
    An NUnit EditMode suite plus deterministic BurstNav/… editor checks runnable in -batchmode.

⚠️ Scope & Known Limitations

🛑 2.5-D Navigation (XZ only)

  • Pathfinding and steering operate on XZ only: no stair/ramp following, agent Y is never modified by the pipeline (gameplay code handles vertical movement).
  • Multi-floor navmeshes flatten into one layer; a "vertical" path is a straight XZ shortcut.
  • Pathfinding throughput is capped at ≈ 256 new requests/frame (excess is deferred, not dropped).
  • ORCA is 2-D disk avoidance with a fixed neighbor cap (48); agents with radius > 1 m are warned about, not clamped.
  • Spawn/destination more than one grid cell (2 m) from the mesh → first request fails (BnPathState.Failed) rather than snapping.

⚙️ Installation & Requirements

Requirements

  • Unity 6 (6000.x) only. Minimum supported version is 6000.0 — earlier Unity versions are not supported (the package depends on Unity Entities 6.x, which is published for Unity 6 only).
  • Unity Entities 6.5.0 — pulled in automatically as a package dependency.
  • All other dependencies (com.unity.collections, com.unity.burst, com.unity.mathematics, built-in com.unity.modules.ai) resolve automatically. No manual setup.

Installation

  1. Import the package (.unitypackage) into your project. The Unity Entities dependency is installed automatically on first open.
  2. That's it: the package adds four ISystems (BnCommandSystem, BnDynamicObstacleSystem, BnPathfindingSystem, BnSteeringSystem) to the SimulationSystemGroup of every world. They are inert until your world contains a BnGraphData singleton (produced by baking — see Quick Start) and agents.

Try the sample first

Window → Package Manager (or the Samples Importer dialog) → import "BurstNav Demo" → open Samples/BurstNav Demo/Demo.unity → Play.

Eight agents wander automatically; right-click anywhere in the Game view to command them all to that point. The demo scene carries a baked navmesh and 8 authored agents, so it runs without any extra setup.

💡 The demo's right-click uses the legacy input manager. The stock Unity 6 3D template ships with it disabled — the demo logs a warning at play start in that case (see "Right-click doesn't work" in Troubleshooting & FAQ).

Enabling the verification harnesses (optional, maintainers/CI)

The package ships deterministic headless check harnesses under the BurstNav/… editor menu. They are compiled only when the project defines BN_INCLUDE_HARNESS — a project that merely installs the package shows no BurstNav/… menu items and gains no overhead.

To opt in, create Assets/csc.rsp in your project containing:

-define:BN_INCLUDE_HARNESS

and let Unity recompile. csc.rsp works in both interactive and -batchmode sessions — it is the mechanism required for headless runs such as:

Unity -batchmode -quit -projectPath <p> -executeMethod SnivelerCode.BurstNav.Editor.BnHarnessRunner.RunAll

Input

The optional BnCommandSystem (right-click to command all idle agents to a point) reads the legacy input manager (UnityEngine.Input). If your project has disabled the legacy manager (new Input System only), this system is a no-op — issue destinations from code with BnAgents.SetDestination instead. The package has no Input System dependency.

🚀 Quick Start

The fastest way in: import the BurstNav Demo sample (see Installation & Requirements) — 8 wandering agents, right-click to command them all.

Then, in your own scene:

1. Bake the mesh

Author your navigation geometry with the built-in NavMesh (static geometry + NavMeshBuildMarkup), then:

  1. Add SnivelerCode.BurstNav.Runtime.Components.BnMeshAuthoring to a GameObject.
  2. Right-click the component in the Inspector → Bake NavMesh Data to Authoring. This runs NavMesh.CalculateTriangulation() and caches the triangulation into the component (CachedVertices/CachedIndices). Run it after any NavMesh geometry change — it is the only way the cache is refreshed.
  3. Enter Play — the Baker converts the cached triangulation into the BnGraphData singleton (an immutable blob graph). The graph is rebuilt from the scene cache on every play session.

2. Add agents

Either author BnAgentAuthoring GameObjects in the scene, or create agents at runtime:

using SnivelerCode.BurstNav.Runtime.Components;

// Authoring defaults: Speed 5, RotationSpeed 10, StopDistance 0.5, Radius 0.5,
// AvoidanceWeight 1, TimeHorizon 5.
Entity agent = BnAgents.Create(world, new float3(0f, 0f, 1f));

// Or with explicit configuration:
Entity agent2 = BnAgents.Create(world, pos, new BnAgentConfig
{
    Speed = 2f, RotationSpeed = 10f, StopDistance = 0.5f, TimeHorizon = 5f
});

BnAgents.SetDestination(world, agent, new float3(10f, 0f, 6f));   // → Requested

Runtime-created agents start Idle and move only after a SetDestination. Both BnAgents.Create overloads and SetDestination are main-thread only and schedule no jobs; for mass spawning (hundreds per frame) issue an EntityCommandBuffer instead of looping Create.

⚠️ The spawn position must be within one spatial-grid cell (2 m) of the mesh, otherwise the first request ends in BnPathState.Failed rather than snapping. Spawn agents on the mesh.

3. Dynamic obstacles (optional)

using SnivelerCode.BurstNav.Runtime.Systems;

// Debris: block a single graph link (main-thread only, asserted in debug builds).
BnDynamicObstacleSystem.SetLinkBlocked(world, linkIndex, true);

// Doors/water: an ECS entity whose Closed state drives a polygon tag —
SystemAPI.SetComponent(doorEntity, new BnDoorComponent { Tag = 0, Closed = true });  // close
SystemAPI.SetComponent(doorEntity, new BnDoorComponent { Tag = 0, Closed = false }); // open

Affected agents re-path within 1–2 frames — see Dynamic Obstacles & Doors.

🧠 How It Works

BurstNav is a 2.5-D (XZ-plane) navigation pipeline built from three stages — bake → path → steer — plus a dynamic-obstacle layer. Everything runs as ISystems with [BurstCompile] jobs; there is no per-agent MonoBehaviour cost.

Bake (editor, at scene bake time)

Baker<BnMeshAuthoring> takes the cached NavMesh triangulation, then:

  1. Welds duplicate vertices (1 mm precision key) and builds directed portal links with center-distance costs and the per-polygon tag-mask union.
  2. Computes a uniform XZ spatial grid (cell size: GridCellSize, or auto = median of the longest triangle edge; doubled with a warning until the grid fits in 4,000,000 cells).
  3. — when HpaEnabled — builds the HPA* cluster graph (capped at 65,534 clusters; over the cap, HPA data is skipped with a warning and flat A* is used).
  4. Writes everything to one immutable blob stored in the BnGraphData singleton entity.

The blob is rebuilt from scene data on every play session and is never persisted to disk (see Mesh Graph Blob Format).

Path (runtime, BnPathfindingSystem)

Agents in Requested state are serviced at a capped throughput (MaxAgentsPerFrame ≈ 256 new paths/frame; excess requests are deferred, not dropped). Each search:

  1. Resolves start/end polygon IDs through the spatial grid (GetPolygonAt).
  2. Runs flat A* for paths shorter than HpaDistanceThreshold (heuristic = XZ distance, cost = portal distance), or HPA* (cluster A* + refinement) for longer ones.
  3. Publishes the winning polygon sequence as a corridor in the agent's BnPolyBuffer.

Steer (runtime, BnSteeringSystem)

  1. A funnel over the corridor yields the local steering point.
  2. ORCA (2-D disks, MaxNeighbors = 48, neighbor discovery via a spatial hash) resolves the actual velocity.
  3. The integrate job moves the agent in XZ only — Y is never touched.
  4. A containment clamp projects positions that would leave the current/next corridor polygon back onto the corridor; a stale corridor (agent pushed/dragged, map changed) triggers an automatic re-request instead of freezing.

Agent state machine (BnPathState)

ValueNameMeaning
0IdleNo active request (initial state; after reaching a destination).
1RequestedDestination set, waiting for the pathfinding system to assign a corridor.
3ReadyCorridor assigned; steering active.
4FailedSearch failed (off-mesh spawn, blocked/unreachable target, budget/overflow). Stays failed until a new SetDestination.

📡 Runtime API — BnAgents

The public runtime surface is intentionally small: one factory class (BnAgents), one config struct (BnAgentConfig), and the dynamic-obstacle API (Dynamic Obstacles & Doors).

Namespace: SnivelerCode.BurstNav.Runtime.Components.

static class BnAgents

Main-thread only (both Create overloads and SetDestination mutate ECS storage directly, schedule no jobs, and are safe to call between frames — e.g. in Update or a system's OnUpdate). For mass spawning (hundreds per frame) use an EntityCommandBuffer instead of looping Create.

public static Entity Create(World world, float3 position, in BnAgentConfig cfg);

// enables BnPathRequestTag. Main-thread only.
public static void SetDestination(World world, Entity agent, float3 position);

The 8 components created by BnAgents.Create

Identical (component-for-component) to what the BnAgentAuthoring baker produces:

ComponentInitial value
LocalTransformspawn position, identity rotation
BnAgentSteeringconfig values, WindowSize = 8
BnPathStateDataIdle
BnOrcaStateMaxSpeed = cfg.Speed, TimeHorizon = cfg.TimeHorizon

The steering pipeline only integrates agents that carry an enabledBnPathRequestTag — a hand-built agent missing any of the 8 components misbehaves silently (frozen, no error). That's why BnAgents.Create exists.

Behavior notes

  • Agents start Idle and move only after SetDestination.
  • The spawn position must be within one spatial-grid cell (2 m) of the mesh, otherwise the first request ends in BnPathState.Failed.
  • SetDestination is the single documented way to request a path at runtime — callers never need to know the tag mechanics.
  • Reaching the destination (within StopDistance) returns the agent to Idle.

🚧 Dynamic Obstacles & Doors

Block and restore navigation at runtime without re-baking. Two mechanisms:

  1. Per-link override — SetLinkBlocked blocks a single graph link (debris, a fallen crate).
  2. Tag masks — BnDoorComponent + per-polygon tag masks handle door/water-style blocking by polygon tag (≤ 16 tags).

BnDynamicObstacleSystem.SetLinkBlocked

using SnivelerCode.BurstNav.Runtime.Systems;

// Main-thread only (debug-asserted).
// linkIndex is the index into the baked graph's Links array (0 .. Links.Length - 1)
// of the BnGraphData singleton. blocked: true = block, false = restore.
public static void SetLinkBlocked(World world, int linkIndex, bool blocked);

Thread contract: the method asserts the main thread in debug builds (a worker-thread call logs an error and does not crash). In release builds the assert compiles out — keep calls on the main thread.

Doors & tag masks

Tags are assigned at bake time on BnMeshAuthoring.PolygonTagMasks (per-polygon bit mask, bit i = tag i, ≤ 16 tags). A link inherits the union of both polygons' masks, and is blocked when that mask intersects the runtime blocked mask:

// Bake-time: tag the polygons (on BnMeshAuthoring, then re-bake).
mesh.PolygonTagMasks[12] = 1 << 0;   // tag 0 = "door A"
mesh.PolygonTagMasks[40] = 1 << 1;   // tag 1 = "water" (always blocked: never opened)

// Runtime (main thread, e.g. a MonoBehaviour.Update or another system):
// Door: an ECS entity whose Closed state drives tag 0.
SystemAPI.SetComponent(doorEntity, new BnDoorComponent { Tag = 0, Closed = true });  // close →
// links blocked, affected agents re-path within 1–2 frames
SystemAPI.SetComponent(doorEntity, new BnDoorComponent { Tag = 0, Closed = false }); // open →
// failed agents re-requested

BnDoorComponent fields:

FieldTypeMeaning
TagushortDoor tag (bit index, 0–15).
Closedbooltrue → the tag is blocked this frame.

Any ECS entity with BnDoorComponent in the world contributes to the blocked mask. A link is blocked when its tag mask intersects the blocked mask, or when its per-link override bit is set via SetLinkBlocked.

How re-pathing works

BnDynamicObstacleSystem runs before pathfinding every frame:

  1. Merges door tag masks into BnObstacleState.BlockedTagMask.
  2. Tracks per-link overrides in BnObstacleLinkFlags.
  3. On frames where anything changed, schedules a Burst job that marks affected Ready agents (corridors containing a changed link) as Requested — and re-requests Failed agents on unblock frames.

Steady state costs zero allocations; the affected-agent scan uses a hash set for large change sets and a linear scan for small ones (threshold-internal).

Auto-managed state singletons

Both singletons are created on first use — nothing to set up:

public struct BnObstacleState : IComponentData      // auto-created on first change
{
    public ushort BlockedTagMask;   // OR of Closed BnDoorComponent.Tag values
    public int OverrideVersion;     // bumped on any block/unblock (version tag)
}

public struct BnObstacleLinkFlags : IComponentData  // created on first SetLinkBlocked
{
    public NativeArray<ushort> Value;   // per-link flags, bit 0 = blocked
}

Authoring components

// BnMeshAuthoring : MonoBehaviour — the bake source.
// CachedVertices / CachedIndices — NavMesh triangulation (refreshed only via the
//   context menu "Bake NavMesh Data to Authoring").
// GridCellSize   — float, 2.0 default. <= 0 = auto (median of longest triangle edge).
// HpaEnabled     — bool, true. Bake the HPA* cluster graph.
// HpaDistanceThreshold — float, 500.0. Paths shorter than this use flat A*.
// PolygonTagMasks — int[] (per-polygon tag mask; bit i = tag i, <= 16 tags).

// BnAgentAuthoring : MonoBehaviour — agent template.
// Speed 5.0 / RotationSpeed 10.0 / StopDistance 0.5 (defaults).

Bake rules of note:

  • The Baker runs when the scene is baked into the world (entering Play) and is skipped entirely if CachedIndices is empty.
  • Vertex welding uses a 1 mm integer key; polygon links carry portal endpoints, center-distance cost, and the tag-mask union.
  • Grid cap: if cols × rows would exceed 4,000,000 cells the cell size is doubled (with a warning) until it fits.
  • HPA cap: more than 65,534 clusters → HPA data is skipped (warning), flat A* is used at runtime.
  • Output: BnGraphData { Graph = BlobAssetReference<BnBlobMeshGraph> } singleton entity.

Graph singleton

📦 Mesh Graph Blob Format

Blob lifecycle

BnBlobMeshGraph is an in-memory build artifact. It is constructed by Baker<BnMeshAuthoring>.Bake() every time the authored scene is baked (at play start / subscene load), and lives for the lifetime of the world inside the BnGraphData singleton as a BlobAssetReference<BnBlobMeshGraph>.

The blob is never persisted. The package contains no blob serialization: no SaveBlobAsset/LoadBlobAsset, no SerializedBlob, no file or asset output, and no scene carries a BnGraphData entity.

Consequences:

  • There is no blob version to migrate. When you upgrade the package, the blob is rebuilt from your scene by the new Baker — the old layout never needs to be read.
  • If the blob layout changes between versions, the only thing that could break is your code, if you read BnBlobMeshGraph fields directly (it is a public struct). Code that only uses BnAgents and the documented API is unaffected.

Blob layout

BnBlobMeshGraph — all fields in source order:

PolygonVerticesBlobArray<BnPolyVertices>Per-polygon triangle vertices in XZ

Scene-persisted data

The only persistent mesh data is what the scene file saves on BnMeshAuthoring:

DataTypeSource
CachedVerticesVector3[]NavMesh.CalculateTriangulation() at "Bake NavMesh Data to Authoring" time
CachedIndicesint[]same
HpaEnabled, HpaDistanceThreshold, GridCellSize, PolygonTagMasksauthored fieldsauthored values

These are primitive Unity arrays — stable across Unity 6000.x; no migration. If you change geometry: re-bake the static NavMesh and run Bake NavMesh Data to Authoring on the BnMeshAuthoring object again (the cached arrays only refresh through that menu command).

Compatibility

  • No buyer migration path is needed: the blob is rebuilt from scene data on every play session with the currently installed Baker, so older saved scenes always load correctly with newer package versions.
  • Legacy-blob fallbacks (matters only if you hold an in-memory blob across a Baker change, e.g. via domain reload with the world kept alive):
    • GridCellOffsets empty → GetPolygonAt falls back to a linear scan (GetPolygonAtLinear).
    • HpaConfig zeroed / ClusterCount == 0 → HPA* is off, flat A* is used.
    • Both fallbacks are by design; new bakes always populate the grid and (when enabled) the HPA layers.

Determinism

Bakes and searches are deterministic: the same input (CachedVertices/CachedIndices + authoring settings) always produces the same blob, and the same blob + the same requests produce the same paths — which is what makes the shipped harness checks reproducible.

🏎️ Performance & Tuning

Zero steady-state allocation

The path hot path is allocation-free in steady state: searches run on Burst jobs over the immutable blob and persistent scratchpad arrays (one scratchpad per worker thread, created in OnCreate, disposed in OnDestroy); the corridor (BnPolyBuffer) is the only per-agent runtime state. The dynamic-obstacle system's steady state is also zero-allocation.

Throughput & scale

  • Pathfinding throughput cap:BnPathfindingSystem.MaxAgentsPerFrame ≈ 256 new path requests/frame. Excess requests are deferred (the agent stays Requested), not dropped — bursty spawning simply spreads over a few frames.
  • Scale profile: the package targets hundreds to low-thousands of agents on a single baked mesh. Agent count is bounded by ORCA neighbor discovery (O(n) in agents per 2 m × 2 m cell).
  • ORCA limits: 2-D disk avoidance with a fixed neighbor cap (BnOrca.MaxNeighbors = 48); agents with radius > BnSpatialGrid.MaxAgentRadius (1 m) are warned about, not clamped.
  • Determinism: bakes and searches are deterministic (same input → same blob → same paths), which makes the shipped harness checks reproducible in CI.

Main-thread contracts

BnAgents.Create / BnAgents.SetDestination and BnDynamicObstacleSystem.SetLinkBlocked mutate ECS storage directly. They are main-thread only and schedule no jobs — safe to call from Update or a system's OnUpdate. For mass spawning (hundreds of agents per frame), issue components through an EntityCommandBuffer instead of looping BnAgents.Create.

Practical tips

  • Re-baking is cheap: the blob is rebuilt from the scene cache on every play session — there is nothing to invalidate after a package upgrade.
  • Off-mesh spawns fail loudly, not silently: a spawn/destination more than one grid cell (2 m) from the mesh ends in BnPathState.Failed. Keep agents on the mesh.
  • Corridor containment: agents are projected back onto their corridor if gameplay code pushes them off the mesh — the agent re-requests from the clamped position instead of freezing. The package never teleports agents.
  • Visualization: the package ships no rendering bridge (no Unity.Entities.Graphics dependency). Study the BurstNav Demo's small visualizer (a MonoBehaviour polling agent LocalTransform/BnOrcaState to drive GameObject capsules) for the pattern; for large counts roll your own bridge (e.g. Entities-Graphics-based).

🚑 Troubleshooting & FAQ

Why do my agents stand still?

Check in this order:

  1. Idle state — agents (authored or BnAgents.Create) start Idle and move only after BnAgents.SetDestination(world, agent, pos) (or a right-click via BnCommandSystem, which only targets Idle agents).
  2. Spawn too far from the mesh — a spawn position more than one spatial-grid cell (2 m) from any polygon makes the first request end in BnPathState.Failed; the agent then stays put. Spawn agents on the mesh.
  3. No BnGraphData in the world — the systems are inert until BnMeshAuthoring is baked (see "How do I re-bake…" below). If your world has no BnMeshAuthoring (or the scene with it was not loaded into the world, e.g. a missing SubScene), nothing runs.
  4. Off-mesh destination — a target more than one cell from the mesh also fails the search (Failed).
  5. BnPathRequestTag — the steering pipeline only integrates agents with an enabledBnPathRequestTag. If you hand-build agent entities, use BnAgents.Create — a missing or wrongly disabled tag freezes the agent silently by design.

How do I re-bake after changing geometry?

  1. Move the geometry (obstacles, walls, floor).
  2. Re-bake the built-in NavMesh (Window → AI → NavMesh → Bake) so the static geometry is up to date.
  3. Enter Play Mode — the runtime NavMesh (and therefore the triangulation BnMeshAuthoring reads) only exists while playing.
  4. On the BnMeshAuthoring GameObject, run the context menu item Bake NavMesh Data to Authoring — this is the only way CachedVertices/CachedIndices are refreshed. If the runtime NavMesh is empty, the cache is left untouched and a red log tells you why.
  5. Stop Play (or keep playing) — the Baker rebuilds the blob from the refreshed cache on every play session, so agents re-path onto the new mesh.

The blob itself is never persisted: it is rebuilt from the scene's cached triangulation on every play session, so older scenes always load correctly with newer package versions.

Why are the BurstNav/* menus missing?

The verification harnesses compile only when the project defines BN_INCLUDE_HARNESS (by design — buyers of the package see no extra menus). To enable them, create Assets/csc.rsp with a single line:

-define:BN_INCLUDE_HARNESS

and let Unity recompile. csc.rsp works in interactive and -batchmode sessions; headless run: -executeMethod SnivelerCode.BurstNav.Editor.BnHarnessRunner.RunAll.

Right-click commands don't work — why?

BnCommandSystem reads the legacy input manager (UnityEngine.Input). If your project uses the new Input System with the legacy manager disabled, the system is a no-op. Note: the stock Unity 6 3D template ships with the legacy manager disabled (Project Settings → Player → Active Input Handling = Input System package only), so in a fresh project the right-click path is inactive until you set it to Both. Two options: enable the legacy manager (Active Input Handling → Both), or issue destinations from code: BnAgents.SetDestination(world, agent, position). The demo logs a warning at play start when the legacy manager is disabled.

Also note: right-click only commands agents whose BnPathRequestTag is disabled (i.e. Idle agents); agents already following a path keep their corridor. The click point is raycast against the scene (2000 m) with a fallback to the XZ ground plane, and it must be within one grid cell (2 m) of the mesh.

Can I use stairs, ramps, or multi-floor maps?

No — BurstNav is 2.5-D (XZ only). There is no stair/ramp following and no per-floor layering: a multi-floor navmesh is flattened into one layer and a "vertical" path is a straight XZ shortcut. An agent's Y is never modified by the pipeline; vertical movement (snap-to-terrain, stair blending) is gameplay code's responsibility. See Introduction & Overview → Scope & Known Limitations.

How do I visualize ECS agents?

The package ships no rendering bridge (no Unity.Entities.Graphics dependency). Options:

  • The BurstNav Demo sample includes a small visualizer: a MonoBehaviour polls the agent entities' LocalTransform/BnOrcaState and drives ordinary GameObjects (capsules). Study it for the polling pattern — it is cheap for demo-scale agent counts.
  • Roll your own bridge, e.g. an Entities-Graphics-based one if you already use Unity.Entities.Graphics in the project.

How many path requests can I issue per frame?

BnPathfindingSystem caps throughput at MaxAgentsPerFrame (≈ 256 new path requests/frame). Excess requests are deferred (the agent stays Requested), not dropped — bursty spawning simply spreads over a few frames. If you see agents lagging behind after a mass spawn, that is the cap working; space out SetDestination calls or accept the few-frame lag.

An agent got pulled back onto the map — what happened?

The steering pipeline keeps agents inside their corridor (containment clamp): a step that would leave the current/next corridor polygon is projected back onto the polygon boundary/link, and if the corridor is stale (agent pushed, dragged, or the map changed underneath) the agent re-requests a path from the clamped position instead of freezing. Agents are otherwise never teleported by the package.

Are agent positions deterministic?

Bakes and searches are deterministic (same input → same blob → same paths), and the harness checks rely on it. The ORCA steering step is also deterministic for identical initial state and timing, so replaying the same frames reproduces the same trajectories on the same machine/build.

Does the package depend on the Input System or Entities.Graphics?

No. Only: com.unity.entities, com.unity.collections, com.unity.burst, com.unity.mathematics, and the built-in com.unity.modules.ai (for NavMesh.CalculateTriangulation() at bake time).
